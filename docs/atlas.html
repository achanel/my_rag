Глава 1 · RAG Overview

Сначала без поиска, потом три способа найти контекст

Часть 1 — голая генерация: вопрос сразу в LLM. Часть 2 — тот же пайплайн, но перед генерацией ретривер достаёт одну запись из 28 абзацев corpus.py. Всё считается локально на numpy, без модели эмбеддингов.

pipeline.pyllm.pyretrieval.pycorpus.pyconfig.py

Naive RAG --rag naive

KeywordRetriever считает, сколько слов запроса встречается в записи. Стоп-слова не убираются, поэтому «what», «are», «the» тоже засчитываются.

score = |слова(query) ∩ слова(record)| score = 0 → запись отброшена

Advanced RAG --rag advanced

TF-IDF + косинус. Два режима: --method vector строит TF-IDF заново для каждой пары (запрос, запись) — 28 «обучений» на запрос. indexed строит матрицу 28×V один раз, запрос — одно умножение.

tf = 1 + ln(count) idf = ln((1+N)/(1+df)) + 1 строки L2-нормированы → dot = cos

Modular RAG --rag modular

ModularRetriever(method=…) — диспетчер: по имени выбирает keyword, vector или indexed. Пайплайн не знает, какой ретривер внутри, — в этом и смысл модульности.

METHODS = { "keyword": KeywordRetriever, "vector": VectorRetriever, "indexed": IndexRetriever, }

Проверь себя

Почему «what are the challenges» в naive-режиме находит не ту запись?
keywords() не выкидывает стоп-слова, поэтому лидируют записи, где есть «what», «are», «the». TF-IDF (tokenize()) убирает их и сразу находит запись #24 «…it also comes with its challenges». Проверь в песочнице.
Оба advanced-режима считают TF-IDF-косинус. Почему результаты разные?
VectorRetriever обучает TF-IDF на паре из двух документов: idf видит только запрос и одну запись. IndexRetriever считает idf по всем 28 записям, поэтому слово, которое встречается везде (например «retrieval»), весит меньше. На «how does retrieval find relevant documents» vector ставит первой #7, indexed — #13.
Что вернёт naive-ретривер, если ни одно слово не совпало, и что тогда уйдёт в LLM?
Пустой список. augment() вернёт запрос без изменений, и модель ответит как в части 1, без контекста. TF-IDF-ретриверы так не умеют: они всегда возвращают top_k, даже при сходстве 0.

Косинусное сходство

Главное правило векторного хранилища

Искать можно только той же моделью, которой строили. Хранилище из OpenAI-векторов (1 536 чисел) нельзя спросить вектором all-minilm (384): разные длины и разные «системы координат». Сменил модель — перезапусти --embed.

Проверь себя

Почему collect() не падает, если одна ссылка умерла?
Ошибки requests и парсинга ловятся по одной странице и попадают в CollectionResult.failed, остальные статьи всё равно пишутся в файл. В книжном скрипте одна битая ссылка роняла весь прогон.
Зачем build() создаёт хранилище с overwrite=True?
Чтобы повторный --embed пересобирал хранилище с нуля, а не дописывал те же чанки второй раз. Иначе поиск начнёт возвращать дубликаты.
Что делает SearchHit.__str__ и зачем он нужен?
Возвращает только текст чанка. Так --show-context печатает найденный текст, а не dataclass, хотя search() отдаёт ещё и score с metadata.

Почему только --provider ollama

Интеграции LlamaIndex для OpenAI требуют openai<3 и откатили бы пакет, на котором стоят главы 1–2. Поэтому здесь llama-index-llms-ollama и llama-index-embeddings-ollama, а _ollama_base_url() отрезает /v1 от адреса.

Обход бага: NumpySafeDeepLakeVectorStore

Deep Lake 3.9 (последняя версия под Python 3.14) вызывает np.can_cast на каждом числе, а numpy 2 это для Python-float запретил. Глава 2 не падает: там Deep Lake сам считает эмбеддинги. LlamaIndex передаёт готовые float, поэтому прокси _NumpyEmbeddingStore перед add() переводит их в np.float32.

Проверь себя

Какие индексы строятся без единого вызова LLM?
vector (нужны только эмбеддинги) и list (вообще ничего не считает). tree пишет сводки, keyword извлекает ключевые слова — обоим нужна LLM уже при сборке.
Почему у vector-индекса своё хранилище, а не vector_store из главы 2?
Интеграция LlamaIndex пишет в Deep Lake с другой схемой датасета, чем «сырой» deeplake.VectorStore из главы 2. Поэтому DEFAULT_INDEX_STORE отдельный: data/processed/index_store.
Зачем IndexQueryEngine строит индекс лениво?
Конструктор дешёвый: индекс собирается при первом обращении к свойству index. Так объект можно создать и передать дальше, не запуская дорогую сборку раньше времени.

Это грубая эвристика из книги: она меряет, насколько ответ «про то же», а не насколько он верный.

Какой снимок нашёлся

cos(вопрос, label_text)

Реальный прогон image-модуля на твоих 20 снимках, топ-10. Шкала от 0 до 0,5.

Почему 00000 с 21 грузовиком проиграл

Документ снимка — список разных классов без количеств. У 00000 это «pedestrian truck tricycle bicycle», у 00014 — «van car truck». Короткий документ из одних машин ближе к вопросу про грузовик, хотя самих грузовиков на 00014 всего два.

Зачем классы без повторов

В книге на каждую рамку пишется метка. На снимке 00010 рамок 211, из них 187 pedestrian, а у all-minilm контекст 512 токенов. Повторы съели бы его целиком, а для поиска важно только, есть ли класс на снимке.

Что вообще есть в 20 снимках

рамок по классам

Всего 1 059 рамок. «ignored regions» и «others» никогда не становятся целевым объектом (_UNANNOTATED).

Проверь себя

Что будет, если в найденном снимке нет класса из вопроса?
target_label возьмёт самый частый класс снимка (кроме ignored regions и others), и CLI напечатает, какой именно объект анализировался. Ответ тогда может быть не про то, о чём спрашивали.
Чем этот выбор объекта отличается от книги?
Книга спрашивает vision-модель про unique_words[0] — первое по алфавиту слово найденного текста, никак не связанное с вопросом. Здесь объект берётся из самого вопроса.
Почему к вопросу для vision_score добавляется «trucks»?
Так сделано в книге: ответ vision-модели описывает объекты в рамках, и сравнение с «вопрос + объект во множественном числе» ближе к тому, о чём она говорит. Это та же эвристика, что и сама оценка.
